# Symmetry reuse in the resident Oracle table

The existing Lean results support policy reconstruction under transformed account units and constraints. They do not establish that four regions of the current table contain the same values. No signed-exposure cells have been removed from the running comparison.

`LongEntryReduction.lean:262` defines `chooseFromLongEntries` as the better of `originalChoice` and `reciprocalChoice`. The reciprocal call receives a different account, tick, feasibility predicate and continuation score. Its score is evaluated through the inverse action mapping. This proves reuse of one optimization primitive for both queries; it does not eliminate the second query or equate its values to the first query's values.

The chronological currency exchange in `EntryExitDuality.lean` sends exposure to `1-e`, price to `1/p`, and funding to its reciprocal. `LimitOrderAdmissibility.lean` transports order traffic, collateral and admissibility. `LimitOrderPolicyDuality.lean` also transports the terminal predicate and objective. In particular, an original cash terminal state becomes fully invested in the exchanged units. The running planner's exposure bounds `[-2,2]` would become `[-1,3]`, and its ordinary price tick lattice becomes a reciprocal lattice. Copying the original rules or cash terminal condition into that second problem would not implement the theorem. The native numerical kernel currently assumes a uniform price tick and quote-sized order limits; the theorem's reciprocal engine is more general.

The long/short endpoint identity `PolicySymmetry.adjusted_lot_time_reversal` reverses an individual lot's entry and exit prices. The module explicitly distinguishes that cashflow equality from chronological feasibility. `PolicySymmetryConstraints.lean` contains a liquidation counterexample to treating the reversed lot as a feasible unchanged-account policy.

For a reusable value entry, the cache key must contain the complete problem context, including market state/law, execution constraints and terminal objective. Schematically, the theorem gives `V_P(s) = V_{D(P)}(D(s))` when the objective is transported into the original units. It does not give `V_P(s) = V_P(D(s))`. A canonical transformed key can share a result when both equivalent full queries occur. Creating a new transformed query for each original short state merely changes its representation; it does not reduce the number of distinct values that must be computed. The current market cloud has no construction guaranteeing paired transformed laws or terminal problems.

Two exact forms of reuse are already present:

- The table indexes post-rebalance wealth, exposure and the pending-order set. It has no separate entry/exit axis. All actions reaching the same complete post-state use the same continuation value; their execution costs have already changed their resulting wealth.
- `oracle_account_grid.py` enumerates order multisets with `combinations_with_replacement`. Permuting the order labels does not allocate another cell. With eight order types and at most two orders, there are `1+8+36=45` books, compared with `1+8+64=73` ordered-book combinations.

As a numerical guard against an invalid same-law sign merge, `data/backtests/oracle-table-symmetry-audit/sign-values.json` evaluates two valid post-decision accounts with wealth 10,000, exposure +0.5 or -0.5, no orders, and price moving from 100 to 101. The actual Oracle arrival and valid complete-close functions give terminal wealth 10,047.475 and 9,947.473736868435 respectively. Both pass the configured maintenance and order-size checks and use the actual 0.05% taker fee. This is a deterministic one-step distribution, so its terminal log values are exact. This example refutes merging those entries under an unchanged law; it does not refute the transformed-problem correspondence.

A fourfold memory/compute reduction would require additional equality and coverage results for the concrete discretized operator and its full transformed cache keys. The existing reconstruction proofs alone do not supply that reduction. In particular, there is no remaining factor of two from a separate entry/exit table in this implementation.

The shared-domain interpretation is valid: one universal table can accept both original and reciprocal queries. Write a complete query as `z = (time, account, market law, execution rules, terminal objective)`. With the objective expressed in transported original units, the proven duality identifies `z` and `D(z)`; a canonical key for this pair can store one value estimate. It need not allocate a separate reciprocal table. However, a fixed-context table is only one slice of that universal domain. Its account cell `D(s)` still uses the slice's original law and rules unless these inputs are also transformed. Consequently, overlap of account coordinates alone is not a cache hit. An off-grid transformed query can use interpolation or a nearby cached estimate as a proposal/control, but its discretization error and changed sampling law remain to be accounted for. This is the same distinction between exact reuse and approximate warm starts that applies when shifting the table in time.

There is a separate, directly measurable source of cross-target reuse: distinct action descriptors can execute to an identical complete post-state within the same root query. `data/backtests/oracle-table-symmetry-audit/duplicate-proposals.json` reconstructs eight baseline decisions. At update 300, 817 proposals contain only 529 numerically distinct post-states; at update 3,300, 829 proposals contain 624. Duplicate fractions among the nontrivial inspected decisions range from 16.2% to 35.7%. Update 10 has only one proposal. These are root-proposal counts, not a measured reduction of the whole continuation table or overall runtime.

`ml/oracle_root_aliases.py` is connected to full root censuses using byte-identical float64 rows within one common law/rule/continuation context. It preserves first-descriptor order and scatters results back to all original descriptors; it conservatively keeps differently signed zeros separate. Partial root plans remain separate because their requested edges can differ by descriptor. Three CPU tests and two GPU integration tests pass, including every conditional outcome and support flag, both limit-fill directions, three remaining-horizon cases, complete score/control equality, reference grading and partial-sampling behavior. The final focused planner suite passes 30 tests and the server suite passes 12.

The paired full-size benchmark at update 3,300 found 624 unique proposals among 829 descriptors. Including the cash reference, physical evaluations fell from 6,640 to 5,000. Ten alternating timed pairs had identical fronts and controls in every case; median root time fell from 85.735 to 80.457 ms (about 6.2%). `data/backtests/oracle-root-alias-benchmark/results.json` records the individual timings and exact tested source hashes. This is a measured root-only improvement from identical post-state reuse, not a fourfold global symmetry reduction. The 90-minute replay measurements predate this exact optimization. A final real HTTP/CUDA worker restart test passed afterward.
