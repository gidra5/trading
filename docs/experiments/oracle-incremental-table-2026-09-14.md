# Resident incremental Bellman table

The implementation keeps the one-hour continuation field on the GPU and updates its interior values incrementally. Its physical buffer is a time ring: advancing one second changes the index and retains existing values without copying the whole field to/from the CPU.

The selected implementation retains the baseline row scheduler and adds exact duplicate-post-state reuse at the root. Both completed 90-minute scheduler trials ended flat at 9,981.0128 from 10,000 (-0.1898721%), with all 5,400 account states identical. The selected scheduler took 68.79 minutes including three reference sweeps, or 37.04 minutes excluding them. All 2,100 audited countdown decisions had finite reference actions; maximum measured selected-action CE regret was 0.0270172 bps. These results assess the finite model and menus described below, not the unrestricted continuous optimum. The root reuse optimization was added afterward and separately verified for exact equivalence and timing.

## Current algorithm

`ml/oracle_incremental_table.py` keeps dense account cells and their sampled market-node values. A rolling update completely recomputes the final two layers. It refreshes bounded sets of ordinary rows at rotating depths near both ends, plus frequent work at depth one. These are scheduling priorities, not simultaneous independent forward/backward CUDA passes. Kernels parallelize across account rows, outcomes and candidate actions; dependent depth updates run in order.

Each selected ordinary row uses four importance-corrected next-price draws when its finite-support feasibility check permits this and it has a complete prior control vector. Uncached rows, unsupported rows and cash-reference rows receive all eight outcomes. Controls remove the known log-wealth offset before caching and are stored per absolute timestamp and account/market row in an LRU capped at 100,000 rows. Dense visit and local variance arrays remain allocated. An evaluated edge applies Oracle transitions and maximizes the next-action menu against the shared next-layer field. It is not a complete simulated path through the whole hour.

For a full root census, byte-identical complete post-states share one outcome evaluation within the common forecast/rules/continuation context. Results are scattered back before descriptor-specific centering, control updates and tie breaking. Partial root sampling retains separate evaluations because descriptor-specific plans can request different outcomes. Reports distinguish logical outcome slots from physical evaluations. This reuses identical target states; it does not merge reciprocal queries under unchanged forecast or execution parameters.

After the exact endpoint layers, a separate support repair re-evaluates previously nonfinite rows with a complete census. Newly feasible states propagate backward until a layer's support stops changing. This handles strict-close feasibility as the terminal deadline extends. Ordinary value updates remain bounded and sampled. Observed counterfactual innovations, evaluated against the old field, old action menu and old terminal date, prioritize those ordinary rows. They never modify probabilities or add a global value correction.

The completed trial evaluated all eight root outcomes to isolate the error from bounded interior updates. It uses 41 exposure representatives from -2.5 to 2.5 in increments of 0.125, three wealth points, up to two orders, two price bins, four signed-size bins, eight market nodes and eight conditional outcomes. Feasibility still enforces the stricter entry bounds of -2 to 2. The root also samples within account cells; future menus use 50 catalog candidates plus retained-order/exposure choices and valid full closing. This is not a 0.01 exposure grid or a continuous-action optimality certificate.

## Initial measured profile

Artifacts: `data/backtests/oracle-incremental-table-profile/`.

Sixteen rolling one-hour updates completed in 14.18 seconds including initialization and first-use overhead. Median update time was 0.467 seconds; maximum was 5.252 seconds. The resident value buffer occupies 1,275,264,000 bytes. The available full-update reference at observation two selected the same action, with zero measured relative CE regret. This one comparison does not establish accumulated planning accuracy.

## Longer evaluation

`data/backtests/oracle-incremental-table-90m/` planned 5,400 observed seconds. Planning was intended to roll at one-hour depth for the first 1,800 seconds, then shrink to the common terminal time with an actual valid flat close. Full finite Bellman sweeps at updates 300, 1,800 and 3,600 were scheduled to independently grade the table and selected root action. Reference values never refresh the tested sampler.

The trial was stopped after 690 observations because its first reference check failed table accuracy. At update 300, the selected root action matched, but the maximum finite-cell log-value error was 2.2835, RMS error was 0.013803, and 393,486 support entries disagreed. The reference cost 920.47 seconds. Ordinary updates had median 0.529 seconds. There is no completed terminal return. This is evidence that a root action match alone was insufficient.

Two concrete problems were addressed: partially populated controls included a large known account-size offset, producing artificial variance, and stale terminal-close infeasibility propagated into the rolling table. The first corrected diagnostic, `oracle-incremental-centered-64s`, used a fresh 64-second initial solve and completed 400 real observations in 233.02 seconds plus a 13.64-second initial sweep. It stayed in cash and its full execution/price audit passed. Maximum finite-cell errors at four rolling checks were 1.52–2.73 log-value bps, but up to 72,074 feasible cells were still missed; none of the checked infeasible cells was falsely marked feasible. These results isolate the support-repair work, not one-hour accuracy.

The follow-up `oracle-incremental-support-64s` adds that backward support repair and completed all 400 observations. All five reference checks (updates 16, 64, 128, 256 and 360) have zero support disagreements, zero measured selected-action regret, and maximum finite-field log errors of 1.52, 2.80, 2.64, 2.66 and 2.68 bps. It stayed in cash; the independent audit passed all 400 transitions, all 401 immutable prices and terminal flatness. Median update time including the infrequent reference decisions was 0.619 seconds. This is a 64-second diagnostic, not a one-hour accuracy result.

`oracle-incremental-support-90m` completed all 5,400 observations with full reference checks at 300, 1,800 and 3,600. It saved the table, control cache, residual statistics and executed account every 300 accepted nonterminal observations. Both the backtest and persistent paper worker call the same `IncrementalController` account lifecycle. Startup implementation identities are checked before checkpoint publication, so editing a running table's implementation cannot silently produce a mislabeled snapshot.

## Persistence and worker integration

The final implementation passed 30 focused planner/alias tests and 12 server controller/service tests. The alias tests compare every GPU outcome and support flag, preserve full and partial root scores, controls, descriptor tie breaking and reference grading, and retain the existing full-sweep, ring-wrap, strict-close and checkpoint tests. A paired ten-repeat full-size root benchmark at update 3,300 reduced 829 proposals to 624 evaluated unique proposals (plus a cash reference): 6,640 logical outcomes became 5,000 physical evaluations. Median root time changed from 85.735 to 80.457 ms, with bit-identical fronts and controls in every pair. This is a root-only timing result, not a measured end-to-end speedup. See `oracle-root-alias-benchmark/results.json`.

The real local HTTP-to-CUDA/NSF worker smoke test completed 14 observations, restarted from the first saved boundary, and ended flat in 10.68 seconds using the final sources. It exercised actual process transport and checkpoint loading, not an exchange. Artifact: `oracle-incremental-alias-http-smoke/results.json`. Its small eight-second planning table tests integration; the separate full-size replay and restore audit supply the larger runtime and persistence measurements.

`oracle_incremental_checkpoint.py` preserves the physical ring, head, horizon, update number, dense visits/variances, observed residual statistics, ordered control cache, root controls and executed front proposal. Checksums and implementation/context identities are checked before restoration. A new snapshot is published through an atomic pointer replacement; the current and preceding successful snapshots are retained. The format is explicitly separate from certified finite-census archives.

`IncrementalController` uses the shared Oracle account lifecycle for input validation, funding, committed fills, aggregate quote caps, failure handling and terminal close. The persistent paper worker accepts `planner: "incremental"`, CUDA, `refresh_every: 0`, an explicit `table_budget`, and optional `root_draws`. The existing repair planner remains available as a reference. No exchange orders are submitted.

Worker responses retain at most 32 individual layer-update records (the first and last 16) while preserving aggregate counts. This prevents a long support repair from exceeding the server transport's message limit. The controller's original record and backtest logs remain complete. A 3,600-layer diagnostic test checks the payload bound and preservation of totals and source records.

`ml/audit_oracle_incremental_checkpoint.py` independently checks a published replay snapshot on CPU: all file checksums, saved implementation/model identities, ring dimensions and timestamp, selected account against the accepted execution log, and bounded observation counts. It also invokes the independent execution ledger auditor, optionally checking immutable source prices. Its two tests pass; the seven worker protocol tests and twelve server controller/service tests also pass. These persistence and transport checks do not establish Bellman accuracy.

The earlier complete baseline suite passed 40 tests: 15 table/worker/observation/checkpoint tests, six guided-sampling/kernel/proposal tests, and 19 existing controller/worker/checkpoint tests. The final focused rerun and HTTP validation are reported above. They include full-sweep agreement, ring wraps and shrinking horizons, CPU root scores, per-node order feasibility, exact restoration of subsequent sampling/decisions, constant normalized-value centering, and propagation of newly feasible multi-tick closes despite a one-row ordinary update budget. The GPU worker completes a restart through an exact flat terminal close using the full root census. The innovation test checks zero mean under the same finite forecast law without modifying values, and prevents duplicate proposals from counting as independent observations.

`TradingTheory/IncrementalSupport.lean` proves the generic support operator's monotonicity, exact repair by updating only previously infeasible entries when support expands, and validity of stopping after an unchanged boundary under unchanged prefix operators. It states the domain and monotonicity requirements explicitly. These are support contracts, not a Lean proof of the GPU implementation or a value-accuracy certificate. The module is imported and audited; `npm run theory:check` passed the complete build and axiom audit.

## Remaining accuracy scope

This is a bounded asynchronous approximation, with no global Bellman error certificate. Local sampling variance does not bound errors from stale neighboring cells, maximization, account interpolation, market-node projection or the learned NSF law. Partial root sampling can still introduce decision noise even on a flat market because cached controls follow changing proposals; the evaluated default keeps the root census complete. The original finite-eight-edge survival checks also do not resolve the ideal NSF's unbounded upper-price support under log utility. No numeric price ceiling has been supplied.

That support limitation affects actual decisions in this trial. `log-support-audit.json` checks the initial decision and accepted updates through 1,799: 1,790 of 1,800 post-decision accounts have a one-arrival liquidation witness under the ideal unbounded price support. The first is update 10, at current price 64,871.29, where price 97,247.89 would liquidate the existing short before any pending fills. This is a support witness, not an estimate of that move's probability. With zero-equity liquidation and exact log utility, any positive probability of such an event gives negative-infinite expected utility for that action. The finite-grid reference agreement therefore cannot be described as accuracy against the unrestricted NSF/log-utility optimum. A specified bounded forecast law would have to be implemented and evaluated separately; the current trial has not silently introduced a ceiling or changed utility.
